*The review of what each table exposes found the row level security right (listings, catalog, places and dealer figures public; notes, checklists, homes, settings, searches and devices owner-only; invites admins only; runs signed-in accounts only), but Supabase grants anon and authenticated every privilege, so a policy too loose or a new table without RLS would be writable with the publishable key. `20261024170000_tighten_api_grants.sql` takes every write away from both roles and gives back only the app's own: saved searches, favourites, home and ownership figures (insert, update, delete), deleting invites and devices, and marking alerts read (`read_at` only; no more deleting or rewriting alerts). Later tables start without writes (default privileges); one the app writes needs its own grant. `api_grants_test.sql` checks every table and view. `app/web/_headers` (Cloudflare Pages): HSTS, `nosniff`, no framing (`X-Frame-Options`, `frame-ancestors`), referrer policy, no camera, microphone, location or payment. No full Content-Security-Policy (the WebAssembly build, fonts and photo CDNs would each need an exception).*
## S.2 Old anonymous users pruned ✅
*Every new browser, and every Lighthouse run on a preview, signs in anonymously, and those users were never removed. `prune_anonymous_users()` (pg_cron `prune-anonymous-users`, daily 03:43 UTC; Supabase's own advice for anonymous sign-ins) deletes the anonymous users made 30+ days ago with no session used in the last 30 days (a running app refreshes its session every hour). They own nothing (saved searches, favourites, homes and devices need an account) and foreign keys cascade; accounts are never touched. A visitor pruned this way browses without a session on the next visit (listings are public) and is anonymous again from the start after. `prune_anonymous_users_test.sql`; the SQL tests now stub `auth.sessions`.*
## S.3 Deploys apply what the database is missing ✅
*The S.2 migration was never applied: its deploy was waiting behind S.1's, and the Dependabot merge right after replaced it in the queue (GitHub keeps one pending run per concurrency group); that run's merge added no migrations, so it skipped the database. The `migrate` job now asks Supabase what it is missing (`tool/apply_migrations.sh --dry-run`, which writes `pending=N` for the workflow) and tests and applies whenever something is, whichever merge's run it is; `check_migrations.sh` still refuses a changed migration on a merge.*
## S.4 How to replace each secret ✅
*`docs/hosting.md`, "Replacing secrets": when (at once after a possible leak, otherwise every January with the IUC check; the GitHub token at its expiry, which is already warned), the order (new value everywhere, check, then revoke the old one) and, per secret, where it lives and how to check it: GitHub dispatch token, Supabase secret key (the collector copies it into the Vault for invites), database password, Telegram bot token, Cloudflare token, Firebase service account, Claude token. Kept as they are: the Android signing key (a new one means reinstalling the app), the Web Push keys (only if leaked: how to start over) and the publishable key (public by design).*
## S.5 Android: encrypted session, no backups ✅
*The Android app kept its Supabase session (refresh token) in SharedPreferences, a plain file readable by anyone with a rooted phone or a backup of it. It now lives in `flutter_secure_storage` (AES-GCM, key in the Android Keystore, which never leaves the phone): `core/platform/session_storage.dart`, given to Supabase as its `localStorage` (the web keeps the browser's). An earlier build's session is moved over once and deleted from SharedPreferences (`session_store.dart`, `session_store_test.dart`), so updating the APK keeps the person signed in; if the encrypted write fails the old copy stays. The manifest now says `android:allowBackup="false"` (`tool/android_manifest.py`): no cloud backup of the app's data. Android 12+ still copies data when moving to a new phone, but the Keystore key doesn't come along, so the new phone starts signed out. `path_provider_android` (from flutter_secure_storage) is held at 2.2.23: 2.3 moved to JNI like `shared_preferences_android` 2.5, which fails in the release APK.*

# Fewer requests (R) 🟡

*Rafael, 2026-10-22, after the caps were removed (9.6e): "is there anything we could cache, or some strategy that would help do fewer requests?" The pages themselves can't be cached: a search page changes with every new ad and every new price, and each listing page is already read only once (9.4b). The savings come from reading fewer pages. Order: measure first (R.1), then the biggest saving (R.2), using the uncapped runs' numbers.*

*Considered, not worth it:*
- *HTTP caching (`ETag`, `If-Modified-Since`): a 304 is still a request, and search pages change all the time.*
- *Compression: Dart's `HttpClient` already asks for gzip, which saves bytes, not requests.*
- *The sites' JSON APIs: `/api/` is blocked by robots.txt.*
- *Parallel requests: forbidden by the Fetching rules.*
## R.1 Pages per search recorded ✅
*Each run stores, for each search, the pages it spans, the pages read and the ads found (`collector_runs.searches`). After a week of uncapped runs these numbers say which of R.2–R.6 are worth building: a search that fits on one page gains nothing from R.2.*

*`fetchSearches` keeps each search's page count from its first page in `searches.json` (`pages`; older manifests have none). `searchReports` (replacing `searchYields`) gives every planned search its pages spanned and read, ads, followed-model ads and whether it was read in full (`removalPlan`'s complete searches). `importBatch` logs one line each, named by its models (`refresh.dart` passes them): "Search (olx): yamaha-mt-07 · read 2 of 3 page(s) · 80 ad(s), 9 followed · not in full"; a search the run never reached reads "0 of ?". `report_run.dart` reads them back (`searchesRead`) into the new jsonb column (migration `20261024220000_run_searches.sql`, `[]` for older runs). "Estado da recolha" shows the last run's searches under "Pesquisas" (`searchReadText`). Tests: `search_manifest_test.dart`, `fetch_searches_test.dart`, `source_batch_test.dart`, `import_steps_test.dart`, `run_status_test.dart`, `collection_status_text_test.dart`, `access_test.sql`.*
## R.2 Light runs, newest first ⬜
*The biggest saving. A light run asks each search for its newest ads first, using the site's own sort, whose parameter is to be found in the sites' sort menu (as was done for the engine-size bands, 9.13). It stops paging once a page reaches ads older than that search's previous read (by the site's dates: Standvirtual's `createdAt`, OLX's `lastRefreshTime`), promoted ads aside. A search of 4 pages then costs 1 request instead of 4.*

*What it can't do:*
- *Light reads are never "read in full", so they remove nothing (`removalPlan`).*
- *A price change on a later page waits for the next full run. Check whether either site moves a repriced ad to the top; if one does, light runs see drops too.*

*Full runs (every page, removals, every price) stay at 2–3 of the 7 hours, e.g. 08:00, 14:00 and 20:00; the rest are light. `refresh.dart`'s `--full` already decides whether a run removes listings; a light run is one without it that also stops paging early. Option: when a search's total count falls in a light run, read that search in full at once (something was removed).*
## R.3 One Standvirtual search per brand ⬜
*If Standvirtual's model filter takes several models (check its filter list), the followed models of one brand share one search. Fewer half-empty last pages: the CB650R and CBR650R as one search of 32 per page instead of two. OLX already groups by family and engine size (9.13, 9.14).*
## R.4 robots.txt kept up to 24 hours ✅
*Rafael, 2026-10-22: "I would do it, yes" (it loosens the Fetching rule "robots.txt read every run"). RFC 9309 lets a crawler keep robots.txt for up to 24 hours. Each site's fetch state (`.fetch_state*.json`, already cached between runs) now keeps the robots.txt read and when (`robots`, `robots_read_at`). `prepare()` uses the kept copy while it is younger than `FetchPolicy.robotsMaxAge` (24 h; a read time in the future, a moved clock, counts as too old) and otherwise reads it again and keeps the new one. A block forgets it, so the first run after the 24 h pause reads it again. The kept copy decides what may be read, as a fresh one would. `refresh.dart` logs when the copy in use was read. With 7 runs a day: about 1 robots.txt request a day per site instead of 7. Tests: `fetch_test.dart` (kept across days and through JSON, the 24 h limit), `fetch_searches_test.dart` (the next run makes no request for it, the kept copy still refuses a disallowed page, a 24 h old one is read again, a block forgets it).*
## R.5 Listing pages that matter first ⬜
*When a run reaches the 30 minutes per site (`maxRunTime`), the Standvirtual listing pages still to read wait for the next run. Read first the favourites', then the alerted ones', then the rest by Deal Score, instead of newest first. Same requests, but what waits is what matters least.*
## R.6 Quiet searches read less often ⬜
*After R.2: a search with no new ad in its last several light reads is read every other light run. Only if R.1's numbers show many such searches.*
